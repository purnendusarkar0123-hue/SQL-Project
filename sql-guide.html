0 · What is SQL, a database, a table?beginner

A database is a set of tables. A table is a grid: columns (fields, e.g. supplier_name) and rows (records, e.g. one supplier). SQL (Structured Query Language) is how you ask questions of those tables.

This project has 10 tables. The one we'll use most is fact_invoice_line — one row per invoice line. A simplified peek:

invoice_numbersupplier_keyitem_keyquantity_invoicedtotal_amount
INV-5000188412121,840.00
INV-500022037739,210.50
Mental model: a query always answers "from which table, give me which columns, for which rows, in what shape."

1 · Reading data — SELECT / FROM / WHEREbeginner

SELECT picks columns, FROM picks the table, WHERE filters rows.

SELECT supplier_name, country, payment_terms_days
FROM   dim_supplier
WHERE  country = 'India';

"Give me the name, country and terms, from the supplier table, for suppliers in India." Use SELECT * to get every column. Filters combine with AND / OR:

SELECT * FROM dim_supplier
WHERE  risk_rating = 'High' AND is_preferred = TRUE;
Try it: list all suppliers with onboarding_status = 'Pending Docs' — these are the onboarding follow-ups (straight from the United JD).

2 · Sorting & limiting — ORDER BY / LIMITbeginner

SELECT supplier_name, payment_terms_days
FROM   dim_supplier
ORDER BY payment_terms_days DESC   -- biggest first
LIMIT  5;                          -- just the top 5

DESC = descending, ASC (default) = ascending. LIMIT caps the rows — essential when a table has thousands.

3 · Summarising — GROUP BY & aggregatesbeginner

Aggregate functions crush many rows into one number: COUNT, SUM, AVG, MIN, MAX. GROUP BY does it per category.

-- total spend per supplier country
SELECT country, COUNT(*) AS suppliers, AVG(payment_terms_days) AS avg_terms
FROM   dim_supplier
GROUP BY country
ORDER BY suppliers DESC;
The golden rule: every column in SELECT must be either inside an aggregate, or listed in GROUP BY. Forgetting this is the #1 beginner error.

4 · Combining tables — JOINsintermediate

Facts store keys, not names (supplier_key = 88, not "Taylor LLC"). A JOIN stitches the fact to its dimension on that key.

-- spend by supplier NAME: join the invoice fact to the supplier dim
SELECT s.supplier_name, SUM(i.line_amount) AS spend
FROM       fact_invoice_line i
JOIN       dim_supplier      s  ON s.supplier_key = i.supplier_key
GROUP BY   s.supplier_name
ORDER BY   spend DESC LIMIT 10;

Table aliases (i, s) keep it short. i.supplier_key means "the supplier_key column from the invoice table."

INNER vs LEFT join — the difference that matters for reconciliation

  • INNER JOIN keeps only rows that match in both tables.
  • LEFT JOIN keeps all rows from the left table, filling NULL where the right has no match.
Why it's the whole game: to find invoices with no goods receipt, you LEFT JOIN PO lines to receipts and keep the rows where the receipt side is NULL. An INNER JOIN would silently hide exactly the problem you're hunting.
-- PO lines that were never received (the NO_RECEIPT exception)
SELECT p.po_number, p.po_line_num
FROM      fact_po_line       p
LEFT JOIN fact_goods_receipt g ON g.po_number = p.po_number
                                AND g.po_line_num = p.po_line_num
WHERE g.gr_number IS NULL;      -- no match on the right side

5 · Conditional logic — CASEintermediate

CASE is SQL's if/else. It turns raw values into business categories — the basis of the match verdict.

SELECT invoice_number,
   CASE WHEN total_amount > 2500 THEN 'Over P-card limit'
        WHEN total_amount > 1000 THEN 'Review'
        ELSE 'OK' END AS flag
FROM fact_invoice_line;

Combine CASE with SUM for "conditional totals" — count/total only rows meeting a condition:

-- P-card spend as a share of total, in one query
SELECT SUM(CASE WHEN pm.is_pcard THEN i.total_amount ELSE 0 END) AS pcard_spend,
       SUM(i.total_amount) AS total_spend
FROM fact_invoice_line i
JOIN dim_payment_method pm ON pm.payment_method_key = i.payment_method_key;

6 · Filtering groups — HAVINGintermediate

WHERE filters rows (before grouping). HAVING filters groups (after). You can't put an aggregate in WHERE — that's what HAVING is for.

-- suppliers we've paid more than $1M in total
SELECT s.supplier_name, SUM(i.line_amount) AS spend
FROM fact_invoice_line i JOIN dim_supplier s ON s.supplier_key=i.supplier_key
GROUP BY s.supplier_name
HAVING SUM(i.line_amount) > 1000000;   -- filter on the aggregate

This is exactly how duplicate detection works: group by supplier + amount, then HAVING COUNT(*) > 1.

7 · Breaking it up — CTEs (WITH)intermediate

A CTE (Common Table Expression) is a named, temporary result you build first and reuse — like a variable for a query. It turns one unreadable nested mess into readable steps.

WITH supplier_spend AS (          -- step 1: compute per-supplier spend
   SELECT supplier_key, SUM(line_amount) AS spend
   FROM fact_invoice_line GROUP BY supplier_key)
SELECT s.supplier_name, ss.spend          -- step 2: use it
FROM supplier_spend ss
JOIN dim_supplier s ON s.supplier_key = ss.supplier_key
WHERE ss.spend > 500000
ORDER BY ss.spend DESC;
You can chain several CTEs (WITH a AS (…), b AS (…)). Every analysis in this project uses them — they're how you keep complex SQL maintainable.

8 · The power tool — window functionsadvanced

Aggregates collapse rows. Window functions compute across a set of rows without collapsing them — so you keep every row and get a total, rank, or running sum beside it. The magic word is OVER().

Ranking

SELECT supplier_name, spend,
   RANK() OVER (ORDER BY spend DESC) AS rnk
FROM (SELECT s.supplier_name, SUM(i.line_amount) spend
      FROM fact_invoice_line i JOIN dim_supplier s ON s.supplier_key=i.supplier_key
      GROUP BY s.supplier_name) t;

Running / cumulative total (the Pareto trick)

SELECT category, spend,
   ROUND(100.0 * SUM(spend) OVER (ORDER BY spend DESC)
              / SUM(spend) OVER (), 1) AS cumulative_pct
FROM (SELECT category, SUM(line_amount) spend FROM v_spend GROUP BY category) c;

Two windows at once: SUM() OVER (ORDER BY …) is the running total; SUM() OVER () (empty) is the grand total. Divide them → cumulative share. That's the 80/20 curve on the dashboard.

PARTITION BY — "restart the window per group"

-- each supplier's biggest single invoice line, kept alongside every line
SELECT supplier_key, invoice_number, line_amount,
   MAX(line_amount) OVER (PARTITION BY supplier_key) AS supplier_max
FROM fact_invoice_line;
When to reach for a window: any time the question has the word "each", "running", "rank", "top-N per", "share of total", or "compared to the group".

9 · Saving logic — VIEWSadvanced

A view is a saved query you can treat like a table. Build the hard logic once, query it forever. This project saves two: v_three_way_match and v_spend.

CREATE VIEW v_spend AS
SELECT i.invoice_number, s.supplier_name, it.category, i.line_amount, pm.is_pcard
FROM fact_invoice_line i
JOIN dim_supplier s ON s.supplier_key=i.supplier_key
JOIN dim_item     it ON it.item_key=i.item_key
JOIN dim_payment_method pm ON pm.payment_method_key=i.payment_method_key;

-- now spend analysis is a one-liner:
SELECT category, SUM(line_amount) FROM v_spend GROUP BY category;

10 · Capstone — build the three-way matchadvanced

You now have every piece: LEFT JOIN (to keep unmatched rows), CTE (to roll up receipts), CASE (the verdict), aggregates. Assemble them and you've written the control this whole project is built on:

WITH gr AS (
   SELECT po_number, po_line_num, SUM(quantity_received) AS qty_received
   FROM fact_goods_receipt GROUP BY po_number, po_line_num)
SELECT p.po_number, i.invoice_number,
   CASE WHEN i.invoice_number IS NULL              THEN 'NO_INVOICE'
        WHEN gr.qty_received  IS NULL              THEN 'NO_RECEIPT'
        WHEN i.quantity_invoiced > gr.qty_received THEN 'QTY_OVERBILL'
        WHEN ABS(i.unit_price_invoiced - p.unit_price) > p.unit_price*0.02
                                                 THEN 'PRICE_MISMATCH'
        ELSE 'MATCHED' END AS match_status
FROM      fact_po_line       p
LEFT JOIN gr                 ON gr.po_number=p.po_number AND gr.po_line_num=p.po_line_num
LEFT JOIN fact_invoice_line  i ON i.po_number=p.po_number AND i.po_line_num=p.po_line_num;
