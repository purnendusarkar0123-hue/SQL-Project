The data model — a star schema

Facts are the events of the P2P cycle; dimensions are the context (who, what, when). The grain of every fact table is one document line — because reconciliation happens line by line, not at the invoice header.

The crown jewel — the three-way match

Procurement's core financial control: never pay an invoice unless it agrees with what we ordered (PO) and what we received (GRN). This whole project exists to express that control as one SQL view and then measure what it catches. A 2% tolerance band ignores rounding noise.

-- sql/02_marts.sql  (abridged): PO ↔ GRN ↔ Invoice, line by line
CREATE VIEW v_three_way_match AS
WITH gr AS (   -- roll up multiple receipts per PO line
  SELECT po_number, po_line_num, SUM(quantity_received) AS qty_received
  FROM fact_goods_receipt GROUP BY po_number, po_line_num)
SELECT p.po_number, p.po_line_num, i.invoice_number,
   ROUND((i.unit_price_invoiced - p.unit_price) * i.quantity_invoiced, 2) AS price_var_value,
   (i.quantity_invoiced - COALESCE(gr.qty_received,0))                 AS qty_var,
   CASE
     WHEN i.invoice_number IS NULL                    THEN 'NO_INVOICE'
     WHEN gr.qty_received  IS NULL                    THEN 'NO_RECEIPT'
     WHEN i.quantity_invoiced > gr.qty_received       THEN 'QTY_OVERBILL'
     WHEN ABS(i.unit_price_invoiced - p.unit_price)
                       > p.unit_price * 0.02        THEN 'PRICE_MISMATCH'
     ELSE 'MATCHED' END AS match_status
FROM fact_po_line p
LEFT JOIN gr                ON gr.po_number=p.po_number AND gr.po_line_num=p.po_line_num
LEFT JOIN fact_invoice_line i ON i.po_number=p.po_number AND i.po_line_num=p.po_line_num;

The nine analytical questions

Each reads from the marts above. Full SQL with commentary lives in sql/03_analysis.sql; the highlights:

Q2

Where does the money go? (spend Pareto)

SELECT category, SUM(line_amount) AS spend,
   ROUND(100.0*SUM(SUM(line_amount)) OVER(ORDER BY SUM(line_amount) DESC)
         / SUM(SUM(line_amount)) OVER(), 1) AS cumulative_pct   -- running 80/20
FROM v_spend GROUP BY category ORDER BY spend DESC;
Top 5 of 7 categories carry 75% of spend. A nested window over an aggregate (SUM(SUM(...)) OVER(...)) gives the cumulative share in one pass — the move that signals real SQL fluency. See the Pareto chart →

Q6·Q7

P-card program — the JD gap, filled

P-cards are 11.7% of transactions but under 1% of spend value — small-dollar, high-volume. That profile is precisely why they need a hard per-transaction limit. The query flags every breach of the $2,500 ceiling:

SELECT supplier_name, invoice_number, total_amount
FROM v_spend
WHERE is_pcard AND total_amount > 2500      -- policy ceiling
ORDER BY total_amount DESC;

→ 106 transactions ($281K) over the limit, routed for compliance review. This is the control Amex's commercial side sells and United's JD calls out.

Q8

Duplicate-invoice detection (double-payment control)

SELECT supplier_name, total_amount, COUNT(*) AS times_billed,
   STRING_AGG(invoice_number, ', ')          AS invoice_numbers,
   ROUND(total_amount * (COUNT(*) - 1), 2) AS amount_at_risk
FROM v_spend GROUP BY supplier_name, total_amount
HAVING COUNT(*) > 1 AND total_amount > 500
ORDER BY amount_at_risk DESC;
Same supplier + identical amount on 2+ invoices = the classic duplicate-payment signature. Caught 288 duplicates worth $4.9M in avoidable double-payments.

Also in the file: Q3 top-20 suppliers (RANK()), Q10 monthly price-variance leakage vs contract (~$5.2M/yr). Every result is reproduced live in the dashboard.
